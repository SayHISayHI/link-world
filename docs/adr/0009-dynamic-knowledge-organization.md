# 0009 - Dynamic knowledge organization and user-owned taxonomy

Status: Accepted
Date: 2026-07-07

## Context

The MVP sidebar mixed three different concepts in one untyped string filter: global scope (`All`), processing state (`Inbox` and `Failed`), and content type (`Articles`, `GitHub`, and `Prompts`). This was deterministic for the first delivery, but it could not represent user intent, AI-assisted organization, saved rules, or stable future sync semantics.

AI enrichment already produced a free-form `category` and string tags. Treating either field as authoritative navigation would let model reruns rename or move user data, create duplicate taxonomy, and make the library structure depend on provider availability.

## Decision

- The sidebar has four explicit sections: fixed System Views, user-owned manual Collections, accepted Topics, and Smart Views.
- `object_type`, `lifecycle_status`, and `triage_status` remain separate dimensions. Content type is a list filter, lifecycle describes processing, and triage records whether the user has filed an item.
- `Inbox` uses `knowledge_objects.triage_status`; enrichment does not remove an item from Inbox. Adding a manual tag or collection, accepting a suggestion, or explicitly filing the object changes triage to `filed`.
- `Needs Attention` is a system view over failed objects and unresolved failed or blocked jobs. It is not a content category.
- Manual Collections own explicit membership in `collection_objects`. Archiving a Collection never deletes its objects.
- Topics are canonical `tags` with explicit `object_tags` assignments. Assignment source belongs to the relationship, not to the tag name.
- AI enrichment schema v3 stores bounded `tag_suggestions` with confidence, rationale, analysis identity, and `pending | accepted | rejected | superseded` status. Model output never creates a canonical tag automatically.
- A new successful analysis supersedes only pending suggestions. It never removes user or accepted assignments and never rewrites accepted/rejected history.
- Smart Views persist versioned JSON rules in `collections.query_json`. SQL is generated by the application from the validated rule AST; raw SQL is never stored or accepted through IPC.
- `LibraryViewRef`, `LibraryFilters`, and `LibraryQuery` replace the overloaded `filter_type` string. Normal listing and FTS search use the same resolved view and filter predicates.
- Cursor pagination uses the stable `(updated_at, id)` order. The cursor is opaque to clients and is schema-validated by the backend.
- Organization mutations use stable UUID identities. Collection updates use optimistic `revision` checks; navigation rows expose that revision for conflict-aware edits.
- Organization audit records contain internal IDs and stable action names only. Tag/Collection labels, model rationale, source content, and query text do not enter runtime logs or support bundles.

## Data migration

Migration `0007_knowledge_organization.sql`:

- Adds triage fields and preserves the previous Inbox result for existing captured/parsed objects.
- Extends existing tags, object assignments, Collections, and membership tables without replacing their IDs.
- Adds `tag_suggestions` and indexes for navigation, membership, and pending suggestions.
- Imports deduplicated tags from only the latest historical AI analysis as pending suggestions. It creates no canonical tags and no object assignments.
- Keeps every prior migration immutable and is covered by production-migrator fixtures from versions 1, 2, 3, and the previous release version 6.

## Consequences

- The library remains useful without AI and the user remains the authority over durable organization.
- AI can reduce filing work while uncertainty stays visible and reversible.
- System-view counts and dynamic navigation require indexed aggregate queries and a dedicated Organization service.
- Search scope cannot be implemented as a frontend-only filter; FTS queries must compose with the same backend view contract.
- Collection/tag sync can later use stable IDs, revisions, assignment sources, and archive/tombstone semantics without deriving identity from labels.
- Legacy `get_recent_objects(filter_type)` and `search_hybrid(filter_type)` remain compatibility surfaces for the CLI and old clients, but new UI code uses typed organization commands.

## Alternatives considered

- Use model category directly as the sidebar: rejected because it is unstable, provider-dependent, and not user-owned.
- Make every AI tag immediately visible: rejected because it produces taxonomy drift and duplicates.
- Keep content types as primary navigation: rejected because type is only one filter dimension and does not express user intent.
- Store Smart View SQL: rejected because it creates injection, migration, portability, and sync risks.
- Materialize Smart View membership: rejected for the current version because it creates cache invalidation and unclear ownership; rules are evaluated from source-of-truth fields.

## Revisit when

- Cloud sync requires explicit organization tombstones and HLC conflict resolution.
- Topic clustering needs canonical merge/alias workflows across large libraries.
- Smart View performance requires a derived membership cache with measurable invalidation rules.
- Users need nested Collections or collaborative ownership.
